# 01

Invoke once for this chat, including follow-ups and resumed work, until disabled. Own capability selection and execution; the user need not invoke specialists separately. Preserve the user's host, model, effort, scope and authority. Keep routine work direct.

## Understand the work before choosing methods

Inspect the actual inputs, current artifact and constraints. Work backward from the intended result: which decisions, transformations and checks determine its quality? Identify consequential weak aspects, dependencies and uncertainties, including ones outside the task's apparent discipline. For broad improvement requests, consider what could materially improve the whole result, rather than only polishing the most visible part. Scale this analysis to the task; keep the working route internal or in its existing task entrypoint.

When prior decisions or preferences matter, read the configured shared Home and relevant owning note, follow their sources and resolve stale or conflicting evidence. A path alone does not carry its contents into context.

## Choose contributions, then apply them

Consider skills, native tools, connected plugins/MCPs and recorded runtimes together. Describe the needed improvement before looking for a capability name. Compare plausible methods by what they can change in this work, their inputs, outputs, checks, prerequisites and cost. A familiar name, task-category match or convenient first result does not settle the choice. Compare a materially different approach before committing when the choice is consequential or ambiguous.

A method can improve one decision or check without owning the project. Seek complementary expertise when it addresses an important weakness. When methods overlap, choose by their actual differences; combine them only where each adds value. Resolve conflicting advice against the task and evidence instead of accumulating instructions. Neither using more methods nor repeatedly using the same few establishes quality.

Read the selected complete SKILL.md and needed support, inspect the actual interface, then apply the method to a decision, artifact or verification. Loading or naming a skill is not application. Prefer the smallest useful combination; leave a method unused when its expected benefit does not justify complexity, latency or context.

Use current native summaries first. When insufficient, search fresh metadata for the improvement, operation or failure in a particular weak aspect:

    python3 "<this-skill>/scripts/capabilities.py" CONCEPT OPERATION FAILURE

Resolve this skill's actual folder. Query distinct needs separately when one broad query would crowd out complementary methods. Refine weak matches with alternate concepts or word forms. The helper searches current user/project skill metadata and recorded nstack indexes using lexical word/phrase/plural matches. An exact identifier is a lookup; ranking is a retrieval lead, not a workflow decision. Keep output bounded and read full bodies only for relevant candidates. Discover connected tools and plugins through their actual native interfaces too.

Verify enablement, callability and prerequisites before relying on a capability. For a remaining concrete gap, use find-skills and carry a justified acquisition through source/dependency/rights review, verification and actual use within existing authority. Keep private context out of external searches, heavy dependencies project-scoped, and native opt-ins and trial conditions intact.

## Reassess through completion

Sequence dependencies and parallelize independent work when useful. Give specialists the outcome, inputs, owned scope, authority and checks; keep one writer per artifact, reuse effective workers and verify handoffs. Independent reviewers receive raw artifacts without a favored conclusion. Work directly when delegation is unavailable or adds little.

At meaningful checkpoints, compare the current result with the intended outcome. Reconsider both the next capability and the workflow itself when evidence exposes a weak assumption, a changed need, failure or a better opportunity. Keep, combine, replace or drop methods accordingly. Check whether local improvements leave a more important aspect unresolved. Reuse valid work; avoid repeated catalogue scans, fixed skill rotations or reopening settled choices without new evidence. Stop refining when further work offers no meaningful improvement within scope.

Execute and verify the finished deliverable. Reconcile uncertain external effects before retrying. Save useful durable decisions or corrections in the owning shared note with links and readback; skip routine transcripts and duplicate history. Keep generated host memory separate.

Retain material state and the next action in the existing task entrypoint. Ask only for required access, spending or a consequential missing decision. Report failed checks and real limits honestly. Deliver the result without another default team, framework or audit. Give advice alone only when requested. Do not rewrite 01 autonomously.
